## 基于机器整数的数值计算优化

在 TypeScript 与 JavaScript 的标准语义中，所有数值都抽象为双精度浮点数（`number`）。双精度浮点在尾数范围内可以精确表示安全整数区间 $[-(2^{53}-1), 2^{53}-1]$，因此语言层面看似“兼容整数”。现代引擎也会用 Smi 做局部优化，但这并不等价于语言级的“整数类型语义”。

底层存在 Smi 优化，不代表前端可以直接引入类似 `smi` 的静态类型并删除所有浮点检查。关键原因是：标准 `number` 的整数状态**不具备代数封闭性**。变量即使在初始化时是整数，后续计算也可能逃逸到浮点语义。

### 假想 `smi` 的逃逸示例

```javascript
function sum(arr : smi[]) : smi {
  let total : smi = 0;
  for (let x of arr) {
    total += x;
  }
  return total;
}
```

`total` 在循环中可能溢出，随后退化为浮点语义，导致去优化与额外检查。

---

在 JavaScript 语义下：
- 算术溢出会触发语义退化；
- 除法不整除会产生小数（如 `3 / 2 = 1.5`）；
- 还需处理 `NaN`、`Infinity`、`-0` 等边界。

这使得 JIT 必须持续保留大量运行时检查，显著限制了整数优化空间。很多在 C/C++ 常见的优化无法直接套用，例如：
- `x * 0 -> 0` 在 JS 里可能受 `-0` 语义影响；
- `x / 2 -> x >> 1` 也需要额外语义约束才能安全成立。

## 设计目标：显式机器整数类型

本方案在 TypeScript 侧引入机器整数类型（如 `rawint32`），并通过 metadata 驱动编译器优化。TS 源码层仍可用类型别名保持兼容，但编译语义中将其视为与浮点语义隔离的封闭空间。

开发者使用机器整数类型时，需接受：
- `3 / 2` 截断为 `1`（整数语义）；
- 溢出按未定义行为（UB）处理；
- 编译器可执行更激进的代数优化。

## 强度缩减的语义边界与目标

针对 `rawint32/rawuint32/rawint64/rawuint64` 采用统一约束：

1. **封闭性**：结果始终回到同一机器整数空间。  
2. **溢出策略**：有符号溢出视作 UB，可直接映射机器指令。  
3. **除零策略**：目标是脱离 JS 浮点除零语义。  
4. **无负零语义**：机器整数域不存在 `-0`，可安全应用整数恒等变换。

优化目标分两层：
- **去检查**：`Checked*` -> 纯机器节点，移除 deopt/异常路径开销。
- **强度缩减**：常量乘除模转移位、掩码、魔数除法，降低指令成本。

## 按类型划分的可优化算子

### `rawint32`（有符号 32 位）
支持 `+ - * / %`。除法采用向零截断：

$$
q = \mathrm{trunc}(x / d),\quad r = x - q \cdot d
$$

### `rawuint32`（无符号 32 位）
支持 `+ - * / %`。除法与取模均按无符号语义。

### `rawint64`（有符号 64 位）
支持 `+ - * / %`，与 `rawint32` 同语义，位宽扩展到 64 位。

### `rawuint64`（无符号 64 位）
支持 `+ - * / %`，与 `rawuint32` 同语义，位宽扩展到 64 位。

## 核心重写规则

### A. 基础恒等与常量折叠
- `x + 0 -> x`，`x - 0 -> x`，`x - x -> 0`
- `x * 1 -> x`，`x * 0 -> 0`，`x * (-1) -> 0 - x`（有符号）
- `x / 1 -> x`，`x % 1 -> 0`，`x % (-1) -> 0`（有符号）
- 常量折叠：`K op K -> K'`

### B. 乘法强度缩减
- `x * 2^k -> x << k`
- `x * (-2^k) -> -(x << k)`（有符号）
- 小常量可选加移位链（需成本模型控制）：

$$
x \cdot 3 \to (x << 1) + x,\quad x \cdot 5 \to (x << 2) + x
$$

### C. 除法强度缩减
- 无符号幂次除法：`x / 2^k -> x >> k`（逻辑右移）
- 有符号幂次除法（向零截断修正）：

$$
\frac{x}{2^k} \to \left(x + ((x >> (w-1)) \& (2^k-1))\right) >> k
$$

- 任意常量除法：魔数乘法（`mulhi + adjust + shift`）

### D. 取模强度缩减
- 无符号幂次取模：`x % 2^k -> x & (2^k - 1)`
- 有符号幂次取模（保持余数与被除数同号）：

$$
r = x \& (2^k - 1),\ x < 0 \Rightarrow r = -((-x) \& (2^k - 1))
$$

- 一般常量取模：`x % d -> x - (x / d) * d`

## 在 TurboFan 中的落地

### 关键观察
后端 `MachineOperatorReducer` 已具备大量整数强度缩减能力（如 `Int32Div/Uint32Div/Int64Div/Uint64Div` 的幂次与魔数优化）。本课题增量不在重复实现数学规则，而在于：

1. 在 `RawInt32StrengthReductionPhase` 识别 metadata 标注的机器整数表达式；
2. 将 `CheckedInt* / CheckedUint*` 降为机器节点（先“去检查”）；
3. 交由既有 reducer 继续做后续强度缩减。

### 建议分层
1. **类型判定层**：复用 `MetadataTypeContext`，提供 `IsRawInt32/IsRawUint32/IsRawInt64/IsRawUint64`。  
2. **节点替换层**：在 `rawint32-strength-reduction.cc` 遍历并 `ChangeOp`。  
3. **清理层**：去除失效检查节点及 effect/control 残留。  
4. **后续优化层**：保持机器算子形态，交给现有 reducer。  

### MVP 覆盖
- `CheckedInt32Add/Sub/Mul/Div/Mod -> Int32Add/Sub/Mul/Div/Mod`
- `CheckedUint32Div/Mod -> Uint32Div/Mod`
- `CheckedInt64Add/Sub/Mul/Div/Mod -> Int64Add/Sub/Mul/Div/Mod`
- `rawuint64` 对齐到 `Uint64Div/Mod` 路径

### 主流程示意

```cpp
for (Node* n : all.reachable) {
  switch (n->opcode()) {
    case kCheckedInt32Div:
      if (IsRawInt32(n->InputAt(0)) && IsRawInt32(n->InputAt(1))) {
        TrimCheckedInputsToBinary(n);
        ChangeOp(n, machine()->Int32Div());
      }
      break;
    // add/sub/mul/mod 与 64 位同理
  }
}
```

## 正确性与防错策略

- 仅在 metadata 明确标注时触发，避免污染普通 JS/TS 路径；
- 输入类型不一致则放弃优化；
- 建议增加 `--turbo-rawint-debug-checks`（Debug 下保留断言）；
- 将改写隔离在 `RawInt32StrengthReductionPhase`，降低与前序 typer 耦合。

## 测试与评估

### 功能正确性
按四类类型覆盖 `add/sub/mul/div/mod`：
- 常量折叠（`0/1/-1/2^k`）
- 幂次除模（移位/掩码）
- 非幂次常量（魔数路径）
- 边界值（`INT_MIN`、`UINT_MAX`、除零）

### 图与汇编验证
- `generate_graphs.py`：确认 `Checked*` 节点消失
- `analyze_optimization.py`：统计节点变化
- `generate_assembly.py`：验证 `idiv` 减少、移位/`mulhi` 增加

### 性能评估
建议覆盖：
- 算术热点循环
- 数组遍历累加
- 哈希+位运算混合负载

指标：吞吐（ops/s）与 p95 延迟，对比 `without metadata` 与 `with metadata`。

## 分阶段路线

1. **Phase A（去检查）**：先完成 `Checked* -> MachineOp` 保守替换。  
2. **Phase B（放大收益）**：补齐 `rawuint64` 64 位无符号除模稳定触发。  
3. **Phase C（成本模型）**：对“加移位链”引入架构感知阈值。  
4. **Phase D（回归）**：把预期节点变化固化到 `verify_tests.py`。

---

以上方案目标是以最小侵入打通：

`metadata 类型注入 -> 去检查 -> 既有强度缩减`

从而让四类机器整数在 TurboFan 中获得稳定、端到端的优化收益。

## 2026-03 实测结论与排障说明

### 当前结论（已验证）

- 在 `MetadataBasedGraphOptimizationPhase` 注入 `/0`、`%0` 的 `RangeError` 可以工作，但必须保证 CFG 接线完整。
- 关键实现在 `src/compiler/metadata-based-graph-optimizer.cc`：
  - 对 `JSDivide/JSModulus/SpeculativeNumberDivide/SpeculativeNumberModulus` 建立 `rhs == 0` 分支；
  - 零分支调用 `CallRuntime(Runtime::kThrowRangeError, ...)`，随后接 `Throw`；
  - 非零分支继续原计算；
  - 额外修复：同步重定向该节点 effect users 的 control 到 `if_nonzero`，避免 scheduler CFG 断言。

### 最容易踩的两个坑

1. **改了 C++ 但没重新编译 `d8`**  
   会出现“代码看起来改了，但行为没变化”的假象。

2. **命令行未显式传 `--turbo_metadata_path`**  
   直接运行 `d8 test.js` 时，文件头 `// Flags:` 注释不会自动等价于命令行传参。  
   建议在验证时显式带上 metadata 参数。
